# 监测投影的耗时与优化

监测投影负责把不同来源的观测转换为可以解释、比较的公开曲线：选择有效疾病映射、
处理来源优先级和报告周期、保留来源明细、计算发生率与摘要。
它的计算量应随实际变化增长；一次普通修订不应重新处理所有国家的历史。

## 本轮定位

原日志中的“Surveillance projection”包含数据库读取、来源选择、聚合和元数据准备，
不是纯 Python 聚合时间。JP-25 的真实只读执行计划显示：

- 返回 59,704 条标准化来源记录。
- 每条历史观测重新执行一次类别选择，LATERAL 节点实际执行 60,319 次，累计约 47 秒。
- 独立捕获输入后的纯计算基线约 4.743 CPU 秒，其中来源投影约 3.142 秒，
  国家聚合约 1.400 秒。该 CPU 基线与数据库计时是不同实验，不能简单相加当作发布耗时。

## 已实现的执行方式

完整国家读取先提取不同的来源身份，即来源序列、定义版本、有效本地编码和规范化标签。
类别选择只针对这些身份执行一次，再关联历史观测；映射有效期仍逐观测检查。
类别优先级、有效发布、质量过滤和人口计算保持原语义。
JP-25 的类别选择从 60,319 次减少到 112 次。

纯 Python 路径也复用调用内的来源摘要、报告周期键和疾病切换检查；
空 legacy 输入不再为每个历史点计算没有候选来源的周期匹配。
这些缓存均不跨任务存在，不改变隐藏来源、删除和来源选择的保留规则。

精确增量继续复用已完成的国家和疾病投影，仅读取有变更来源所依赖的疾病。
未知来源、粗粒度标记和不兼容基线仍走完整读取；这些回退路径也使用本轮优化。

实际回补暴露了另一条重复路径：一次日本更新可能精确涉及 68 个疾病，
此时旧的 `requested_categories` 预筛选仍让大部分历史观测逐行选择来源类别。
现在有审核映射的国家在精确目标达到 16 个时也使用来源身份去重查询，
最终仍以 `mapping.target_code IN (...)` 严格限制返回的疾病。
目标为 1–15 个时保持原来的选择性查询；空目标集合直接返回空记录，避免执行没有目标的 SQL。
没有审核映射的国家保持注册疾病过滤。
映射优先级、NULL 编码/标签、有效期、质量和历史快照的规则不变。

`SITE_EXPORT_PROJECTION` 按国家分别记录：

| 字段 | 范围 |
| --- | --- |
| `metadata_seconds` | 频率和来源配置准备 |
| `read_and_select_seconds` | SQL、传输与标准化，以及来源/周期选择 |
| `aggregate_seconds` | 国家聚合、输入摘要、增量合并和展示元数据 |
| `scope` | 完整国家，或本次读取的疾病数 |

完成基线的版本指纹包括来源选择、报告周期与切换政策的实现。
这些规则变化时旧投影不能继续冒充新算法的结果。

映射发布激活会在同一事务内为旧、新发布涉及的国家父级写入粗粒度待更新标记。
撤销映射也会使旧曲线失效；激活失败或回滚不会留下独立生效的标记。
目前失效范围是旧、新国家集合的保守并集，尚未缩小到发生语义变化的类别。

## 实测结果

| 场景 | 优化前 | 本轮优化后 |
| --- | --- | --- |
| JP-25 全历史来源查询、传输与标准化 | 49.248 秒 | 5.085 秒 |
| 同一批 JP-25 输入的纯计算 CPU，5 轮交替中位数 | 3.959 秒 | 2.757 秒 |
| 8 进程、8 地区完整投影阶段 | 70.5 秒 | 19.7 秒 |
| 8 地区完整本地 JSON 导出 | 77.692 秒，复用已有对象 | 27.682 秒，空输出目录新建 504 个对象 |

查询对照分两次在各自一致的只读快照上验证：原查询 49.248 秒 → 身份去重查询
5.916 秒；随后在另一个一致快照上将身份查询 5.654 秒 → 预计算身份查询 5.085 秒。
每次 59,704 条标准化记录逐行相等，SHA-256 相同。
纯计算对照使用同一份独立捕获输入，5 轮原版/新版交替执行，
每轮国家、浏览器和来源完整字典严格相等；中位数减少约 30.4%。
首轮单次 4.743 → 2.946 秒也记录在证据中，但它受到首次运行与预热条件影响。

完整 8 地区实验未复用旧输出目录，所有 504 个公开对象与上一轮全量实验的 SHA-256
全部相同。两次完整实验使用不同只读快照，数据库缓存也未清空，
因此完整耗时表反映实际观测；严格控制的查询与纯计算对照才用于确认单项加速。
新全量实验每 0.2 秒采样的进程树 RSS 峰值约 4.10 GiB，父进程峰值约 693 MiB。

在新初始化基线上模拟一条 D038 修订，导出耗时 4.608 秒，读取/来源选择 0.929 秒，
只更改 5 个逻辑文件并首次创建它们的不可变对象；其余 499 项复用。
这与上一轮已有对象基线的 3.903 秒不是同一对象缓存条件。
所有时间均不含上传、远端指针切换、数据库确认或 HTML 构建，未写生产事实数据。

### 密集精确疾病更新

从实际待发布变更中恢复 JP-25 的 68 疾病集合，在同一个 PostgreSQL 导出的只读快照上，
分别执行旧精确查询和来源身份去重后保留精确目标过滤的查询。每组旧查询只执行一次。
表中范围是 SQL、传输与标准化，不包含后续聚合和发布。

| 目标疾病数 | 旧精确查询 | 来源身份查询 | 标准化行数 |
| --- | --- | --- | --- |
| 1（D038） | 1.285 秒 | 1.347 秒 | 493 |
| 8 | 8.598 秒 | 1.558 秒 | 4,626 |
| 16 | 16.543 秒 | 1.757 秒 | 9,414 |
| 32 | 30.929 秒 | 2.411 秒 | 18,886 |
| 68（实际更新范围） | 57.831 秒 | 3.871 秒 | 38,856 |

每组的标准化记录按原顺序逐行严格相等，没有通过排序消除差异；分别经过
`apply_disease_cutover_projection`、`build_country_data` 和 `merge_country_diseases`
后，包含未变疾病和来源明细的完整国家字典也严格相等。
68 疾病查询约快 14.9 倍，其记录 SHA-256 为
`1999fc5f3688ecff0353cd0cbe76dc5f269976ffb9c73fe14b7d319d8fced59b`。
完整国家字典 SHA-256 为
`acc3fade5b77089ea18836c5581614bc06616b5e16467b08dc9c57cc1d4e66cc`。

阈值 16 对该场景是保守选择：8 疾病也有收益，但单个国家的实验不足以证明
所有来源的最佳阈值都应更低。1 疾病仍保留更快的原路径。
独立 PostgreSQL 回归还对密集查询复用 NULL/类别优先级、as-of 修订和完整国家
字典测试，并检查 0/15/16/32 边界及未选映射目标不会泄漏。
隔离 PostgreSQL 15 中 66 项查询测试全部通过，其中 15 项实际执行 SQL；
与相邻国家增量、输出和工作进程回归一起共 148 项通过。
这次查询源码变更会使已完成投影的版本指纹失效；上线后须从完整只读导出重建基线，
再恢复日常精确增量，不能复用旧算法基线。

常规回归 316 项通过；独立 PostgreSQL 环境中全部 50 项查询测试通过，
其中 4 项实际验证 SQL 的映射、历史读取和完整来源投影语义。
另有 500 次原版/新版差分执行，输出或异常语义相等。

证据在 `data/cache/build-verification/20261107-data-architecture/projection/`。

## 如何进一步取消发布时的历史投影

当前优化直接减少重复计算。更进一步的持续投影应使用独立物化层：

```mermaid
flowchart LR
  I[采集事务：规范事实 + 精确变更日志] --> P[按国家分区的投影任务]
  P --> S[来源与报告周期分片 + 选源统计]
  S --> G[已完成投影版本]
  G --> U[发布器：摘要与不可变对象引用]
```

这部分是后续架构边界，尚未实现新的数据库物化表或浏览器分片协议。
发布器最终可以只读取完成版本，但必须先具备以下正确性条件：

- 删除有明确标记，空分片能够替换旧值；映射变更同时失效旧、新疾病。
- 变更日志覆盖 geography、来源、dimension 和完整报告周期；人口修改按地区和年度失效。
- 保留来源的全历史小型选源统计。新增一个点可能改变代表来源或交接边界，
  此时需要重算对应疾病，不能只截取变更日期。
- 映射、来源描述、人口和政策变化必须使相关物化版本失效；历史 as-of 继续使用修订账本。
- 公开国家/疾病 JSON 仍包含完整数组。若要让写入和传输也完全独立于历史长度，
  还需要浏览器按疾病和年度读取分片。

把原来的全量函数原样移到采集任务不会减少总体计算量。应先去掉本轮已经证实的重复查询，
再依据剩余耗时决定是否引入上述分片物化层。
