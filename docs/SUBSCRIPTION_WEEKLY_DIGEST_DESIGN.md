# Integrated weekly subscription digest

Status: stage-only prototype, not an enabled production pipeline. The currently implemented
`weekly_digest` campaign contains published surveillance reports. Research and
official notices already have separate subscription streams. A single digest
covering all three requires a shared publication window and must replace the
existing weekly-digest producer; merely concatenating the three outboxes can
silently omit later-arriving content or send a second digest for the same week.

## Sources and eligibility

Use a UTC ISO week and record both `observed_at` and each item's original
publication date. Attribute a newly verified public item to the week in which
it was first observed; show the source publication date separately. This avoids
discarding a late published notice or pretending its original date is its
delivery date. Do not backfill before an explicit activation week.

Each source publishes an immutable, public-only observation record:

* Reports: the approved, quality-gated, cross-model accepted report metadata,
  published index and page verified against the R2 manifest, as in
  `report_subscription.py`.
* Official notices: only published, cross-model accepted alerts from a verified
  Situation publication, as in `notice_subscription.py`. Preserve the notice
  status and source URL; do not invent counts or health-risk assessments.
* Research: only cited findings in a published bilingual, quality-gated weekly
  brief, validated by `dispatch_research_digest.py`. Preserve the actual AI or
  editorial review disclosure and source links.

The observation key contains source kind, stable public identifier and public
content fingerprint. Retractions, withdrawn reports, changed notices or changed
briefs invalidate the observation for a not-yet-dispatched issue and require a
fresh verified snapshot. Preserve the event history; never silently mutate a
queued or sent issue. Do not use unpublished, internal, or merely discovered
records to fill missing sections.

## Closing the week and preparing an issue

Run a persistent coordinator separately from the individual dispatchers. After
an explicit cutoff (for example Monday 06:00 UTC), obtain a source checkpoint
from each enabled source confirming successful observation through the cutoff.
This checkpoint must mean a completed public-source scan, including a successful
empty scan; an absent or failed scan is not an empty section. If any required
source has no valid checkpoint, keep the issue pending and emit an actionable
health event. A source deliberately disabled before the week is explicitly
marked disabled in the snapshot, rather than claimed to have no updates.

Build a deterministic snapshot of the latest verified observations for that
week. Store the source checkpoints, release identities, item IDs, fingerprints,
localized excerpts, filters, and the exact payload in a durable shared outbox
before contacting the Worker. The snapshot and a versioned issue key are
immutable; retries reuse the stored payload. Empty successful weeks are recorded
as completed without sending. Enforce Worker limits before staging; if an issue
is too large, halt for review or use a documented stable splitting policy rather
than silently truncating. New observations after a closed checkpoint belong to
the next issue, with their original publication date still displayed.

Each report, notice or research finding is one content item with its own
country and disease facts and its own English and Chinese fragment. Unknown
metadata cannot satisfy an explicit filter. `weekly_digest` currently exposes
country and disease filters; within each dimension values are OR, and all
selected dimensions must match the same item. The Worker checks the current
preferences when preparing delivery, skips a recipient with no matching items,
and rechecks the preference revision immediately before SMTP. Do not apply a
research-only dimension to an unrelated report or notice. Each email retains
links to the relevant published source and a short methodology and review
disclosure. No new AI claims are generated by combining the sources.

## Migration and acceptance

1. Introduce this producer behind a separate disabled flag, explicit activation
   week, separate full/pilot watermarks and a new idempotency namespace. Generate
   shadow snapshots and compare their source counts, item matches and public
   links with independent verified source snapshots.
2. Keep the current report-only weekly digest running during shadow evaluation.
   Reconcile all pending or unknown old deliveries first. For a selected future
   week, switch ownership of `weekly_digest` atomically to the integrated
   producer; leave the separate `reports` list unchanged. Never create both old
   and new weekly-digest campaigns for the same week.
   Migration `0017_weekly_issue_ownership.sql` rejects collisions between the
   two automated producers' canonical keys for one mode and ISO week, including
   revision keys. It does not deduplicate manual campaigns, custom/case-variant
   keys or multiple-list campaigns. Check historical collisions before applying
   it, reconcile queued/sending/unknown deliveries, and decide an explicit
   correction policy; the index also rejects an automated `r2` in the same week.
3. Exercise controlled inboxes for every filter dimension and language, a
   no-match recipient, empty sources, a late notice, a missing checkpoint, a
   corrected or withdrawn item, process restart and concurrent coordinators.
   Confirm actual SMTP acceptance and provider delivery/bounce feedback. Test
   that changing preferences after queueing cannot expose unmatched items.
4. Retain old outboxes and idempotency records during rollback. If an issue has
   already reached the provider, reconcile its delivery outcome instead of
   sending the old report-only issue again.

The stage-only prototype lives in `src/services/data_release/weekly_digest.py`;
`weekly_source_observations.py` provides verified observation scans for reports,
notices and research. These modules are not connected to the scheduler or a
sender. The research scan requires a Pages release bound to a Papers manifest
and validated current article pages; the current production release lacks that
binding, so its research completion receipt is blocked.
The new `/research/evidence-manifest.json` records public article status and
summary hashes, while article pages carry the rendered article JSON hash.
Neither alone proves that the published Pages snapshot and Papers R2 pages are
the same generation; see `docs/PAPERS_RELEASE_IDENTITY.md` before using them
to release this block.
Unrelated publication changes can also block retries until the current source
snapshot is proven equivalent. The atomic cutover and operator monitoring
remain to be implemented.
